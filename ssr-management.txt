DKS Upholstery — SSR and Superfast Data Loading

Overview
- This Next.js App Router project uses server-side data fetching with Incremental Static Regeneration (ISR) for the blog list page, enabling very fast responses from cache while keeping content fresh.
- Cached responses are typically served in tens of milliseconds when warm, depending on hosting and network, with revalidation happening in the background.

How SSR/ISR works here
- Server component: src/app/blog/page.tsx
  - An async server component function fetches data on the server before rendering:
    - getBlogPage()
    - getBlogs()
  - Returns initial HTML + critical data to the client via <BlogClient />.
- Data fetching core: src/utils/api/FetchResponce.tsx
  - fetch() is called with Next.js cache hint: next: { revalidate: REVALIDATE }
  - REVALIDATE is set to 1 (second), meaning ISR revalidates the cached response at most every 1s.
  - Base URL comes from NEXT_PUBLIC_API_HOST_URL (fallback http://localhost:1337), hitting the Strapi API at `${CMS_HOST_URL}/api`.
- Blog listing API helpers: src/utils/api/fetch-urls.ts
  - All exported helpers (e.g., getBlogPage, getBlogs) route through fetchApiResponse(), inheriting the same revalidation behavior.

Why it’s super fast
- Cached HTML/data: After the first request, subsequent requests are served from Next.js cache/CDN until it’s time to revalidate, which is extremely fast.
- Background refresh: When a cached entry is stale (>= 1s old), Next revalidates in the background while continuing to serve the last good response to users.
- Less client work: The initial HTML is server-rendered, reducing client computation and yielding faster TTFB and FCP.

Client interactivity & pagination
- Component: src/components/blog/BlogClient.tsx
  - Receives SSR-fetched data for the initial render.
  - On pagination, it calls getBlogs(page, pageSize) client-side to fetch another page (still using the 1s revalidate policy from the same API helper), then updates local state for a smooth UX.

Blog detail page behavior
- Route: src/app/blog/[slug]/page.tsx
  - Renders a client component (BlogDetailClient) that performs a client-side fetch using getBlogBySlug(slug).
- Component: src/components/blog/BlogDetailClient.tsx
  - On mount, fetches the Strapi document by slug, sets loading/error states, and renders BlogDetail.
- Note: This is CSR for detail pages. If desired, you can migrate to server fetching by turning [slug]/page.tsx into an async server component that calls getBlogBySlug() and passes the data to a server/client boundary component.

Key files and references
- SSR entry (list page): src/app/blog/page.tsx
- Client detail page: src/app/blog/[slug]/page.tsx
- Client listing UI and pagination: src/components/blog/BlogClient.tsx
- Client detail data loader: src/components/blog/BlogDetailClient.tsx
- Strapi request utilities: src/utils/api/fetch-urls.ts, src/utils/api/FetchResponce.tsx

Tuning tips (if you want even faster)
- Adjust REVALIDATE in src/utils/api/FetchResponce.tsx to balance freshness vs cache hits.
- Host Next.js on an edge-enabled platform/CDN for low-latency cache delivery.
- If Strapi is remote, place it near your Next.js host or enable its own HTTP-level caching.
